01

The mental model

Here is all of tilia, in one sentence: tilia(value) returns a reactive proxy with the same type and the same shape as value. Reads and writes are ordinary property access. There is no wrapper API to learn, no .get(), no .set(), nothing to unwrap. Your domain model stays your domain model — it just becomes observable.

Reactivity is pull-based: a value is computed when something reads it, and invalidated when one of its dependencies changes. Nothing recomputes eagerly in the background. Nested objects become reactive on first access, so one call at the root of your model is enough.

If you keep one thing from this page, keep this: you never talk to tilia, you talk to your data. Everything that follows — tracking, computed values, observers — is just what happens around ordinary reads and writes.

Getting started

Install the package:

The smallest complete loop is three steps: create a tilia object, observe it, change it. The observer runs once immediately, then re-runs whenever a value it read changes.

That is the whole ceremony. No store setup, no provider, no action definitions — the rest of this guide is about what tilia does with the reads and writes you were already making.

03

Tracking

How does tilia know what to re-run? While an observer runs, tilia records every property it reads. Those reads become the observer's dependencies. When any of those properties is written, the observer re-runs — and its dependencies are recorded again, from scratch.

Re-recording on every run matters more than it sounds: tracking follows your control flow. A branch that stops reading a value stops depending on it.

Pro tip Tracking is per-property, not per-object. Writing forest.health only wakes observers that actually read health. You get fine-grained updates without selectors, simply by reading what you need and nothing more.

04

Computed values

A computed is a property whose value is derived from other reactive values. You declare it in place, inside the object, and read it like any other field. Pull reactivity applies: the function runs when the property is read, and its result is cached until a dependency changes.

Meet Alice. Her age is not stored anywhere — it is derived from her birth date and a shared now.

Story Alice can grow older :-) — nothing set her age; the world moved, and the value followed. That is the whole promise of derived state: you describe what a value is, and stop writing the code that keeps it up to date.

Chaining computed values

Computed values can read other computed values, and tilia tracks the whole chain. A small store: the subtotal sums the items, the discount depends on the subtotal, the total depends on both. Change a quantity and every downstream value is invalidated — but nothing recomputes until somebody reads it.

Pro tip Because computed values are lazy, a long chain costs nothing while nobody looks at it. Do not hesitate to derive freely — the price is paid on read, once, and cached.

05

Observing

Where computed values derive data from data, observe(fn) pushes data out into the world: the document title, a websocket, localStorage. The function runs once immediately, and re-runs whenever a reactive value it read during its last run changes.

Two rules of thumb keep observers healthy. First, read inside, write outside: an observer that writes a value it also reads is a loop. Second, keep each observer about one effect — small observers have small dependency sets, and small dependency sets re-run rarely.

06

Arrays and nesting

tilia does not stop at the first level. Arrays, and objects inside arrays, become reactive on first access — the proxy spreads through your model as you read it. Mutating methods like push and index assignment are tracked like any other write.

Pro tip An observer that iterates a whole array depends on the whole array. If a view only needs one row, read that one row — grove.trees[3].height — and other rows can change without waking it.

Reference: tilia(value), observe(fn) →

07

React integration

A React component is, from tilia's point of view, just another observer — one whose effect is rendering. useTilia(), called once at the top of a component, tracks the render exactly like an observe run: the component re-renders when a property it read changes, and never otherwise.

Notice what is absent: no selector functions, no context provider, no memoization to get right. Components read the domain directly, and precision comes from the same tracking rule as everywhere else — you depend on what you read.
